# Бэкапы базы и проверка восстановления

Бэкап (дамп) - это полная копия данных `nexus` в одном файле. Он хранится вне репозитория, поэтому
его нельзя случайно закоммитить, и он защищён правами доступа.

## Что где лежит
- Файлы: `~/nexus-backups/nexus-<дата-время UTC>.dump` (каталог можно сменить переменной `BACKUP_DIR`;
  внутри репозитория скрипт откажется работать). Права: каталог 0700, файлы 0600.
- Скрипты: `scripts/backup.sh` (дамп), `scripts/backup_prune.sh` (хранение), `scripts/restore_drill.sh`
  (проверка восстановления), `scripts/sql/bootstrap_backup_roles.sql` (одноразовая подготовка ролей).
- Рядом с каждым дампом лежит файл `nexus-<...>.counts` - число строк в таблицах до и после дампа (для проверки восстановления).
- Хранение (даты по UTC): по одному самому свежему дампу за каждый из 7 последних дней, в которые бэкап был,
  плюс по одному самому свежему за каждую из 4 более старых календарных недель (ISO), не покрытых этими днями.
  Остальные дампы удаляются вместе с `.counts`. Самый свежий дамп не удаляется никогда. Если бэкапов не было
  несколько дней, окно не "сгорает". Значения `KEEP_DAILY` / `KEEP_WEEKLY` (целые, не меньше 1) можно
  поменять переменными окружения; неверное значение - ошибка, ничего не удаляется.
- Каталог бэкапов скрипт создаёт только вне репозитория, не равный `$HOME` и не его родитель; существующий
  каталог с правами не 0700 он отвергает (права сам не меняет).

## Один раз: создать роли (нужно ваше решение)
Скрипт SQL создаёт роль `nexus_ro` (только чтение, для дампа), роль `nexus_test_owner` и базу
`nexus_test` (для проверки восстановления), и убирает у остальных право подключаться к `nexus` по умолчанию.
Пароли не используются: роли работают только через локальный сокет внутри контейнера Postgres.
```bash
docker compose -f docker-compose.local.yml exec -T postgres sh -c \
  'psql -U "$POSTGRES_USER" -d postgres -v ON_ERROR_STOP=1' < scripts/sql/bootstrap_backup_roles.sql
```
Скрипт можно запускать повторно - ничего не сломается.

## Сделать бэкап
```bash
make backup
```
Дамп делается транзакцией только на чтение, сканер не останавливается.

**Ежедневный запуск уже настроен:** 23.10.2026 в вашем crontab установлена строка, которая в 03:15 запускает
`make backup` и пишет журнал в `~/nexus-backups/backup.log`. Важно для WSL: cron работает, только пока запущен
сам WSL (на этом компьютере служба `cron.service` включена через systemd). Если компьютер или WSL выключены
в 03:15, бэкап в этот день пропускается. Журнал `backup.log` сам не ротируется - иногда проверяйте его размер.

## Проверка восстановления (restore drill)
```bash
make restore-drill
```
Берёт последний дамп и восстанавливает его **только** в `nexus_test` (любое другое имя скрипт отвергает;
пользователь для восстановления зафиксирован как `nexus_test_owner`, и перед началом проверяется, что он не суперпользователь).
Затем сравнивает число строк в каждой таблице с числами из файла `.counts` (строки до и после дампа):
значение должно попасть в этот диапазон, у неизменных таблиц - совпасть точно. Отсутствующая таблица или
расхождение - это `drill FAILED` и ненулевой код выхода. Для дампа без `.counts` (сделанного старой версией
скрипта) проверка не запускается: сначала сделайте свежий `make backup`. В `nexus` скрипт ничего не пишет.
Таблица с результатом (только числа) выводится на экран и сохраняется в `~/nexus-backups/restore-drill-last.txt`;
в `docs/reports/restore-drill.md` её нужно перенести вручную (автоматически репозиторий не меняется).

## Как восстановить боевую базу при аварии
Автоматически этого не делает ни один скрипт. Сначала остановите сканер, затем попросите разработчика
выполнить восстановление в новую пустую базу и переключить приложение. Не делайте `docker compose down -v`.

## Внешний пульс (heartbeat)
Бесплатный сервис (например healthchecks.io) ждёт запрос после каждого успешного бэкапа и присылает
оповещение, если его нет. Ссылка-пинг - это секрет: положите её в файл `~/.nexus-heartbeat-url` (права 0600)
и задайте `HEARTBEAT_URL_FILE=$HOME/.nexus-heartbeat-url` (в строке crontab перед `make backup`). Файл должен
принадлежать вам и иметь права ровно 0600, иначе скрипт его проигнорирует и громко предупредит (ссылку в журнал не пишет);
ссылка должна быть обычным `https://...` адресом. В репозиторий и в чат ссылку не вставляйте.
Платный сервис - только с вашего согласия.

**Статус:** по вашему решению от 23.10.2026 внешний пульс отложен до переезда на VPS (этап 2). Сейчас сервис не
подключён, шаг пропускается, а пропущенный бэкап вы заметите только по журналу. Инструкция выше - на будущее.

## Копия на диск C: (вне WSL)
По вашему решению от 23.10.2026 после каждого успешного бэкапа скрипт копирует дамп и файл `.counts` в
`C:\nexus-backups` (в WSL это `/mnt/c/nexus-backups`, вне OneDrive, без шифрования). Каталог создаётся при первом запуске,
если диск C: смонтирован. Копия сверяется контрольной суммой (sha256); хранение такое же, как у основной папки (7 дней + 4 недели).
- Другое место: переменная `BACKUP_COPY_DIR` (пустое значение отключает копию). Внутри репозитория и равное `BACKUP_DIR` место скрипт отвергает.
- Если диск недоступен или копия не удалась, скрипт пишет `WARNING`, сам дамп остаётся и бэкап не считается проваленным;
  в файле статуса будет `"copied": false`, и (после этапа S0b) придёт оповещение в Telegram.
- Это защищает от потери диска WSL (`ext4.vhdx`), но не от поломки всего компьютера: копию на другое устройство делайте отдельно, зашифровав (см. ниже).

## Файл статуса бэкапа
После каждого запуска (успешного и неудачного) скрипт атомарно пишет `last_backup.json`:
`{"finished_at": "...Z", "ok": true, "dump": "nexus-....dump", "copied": true}` - только имена файлов, без секретов.
Проверить вручную: `cat ~/nexus-backup-status/last_backup.json` (то же самое лежит в `~/nexus-backups/last_backup.json`).
`ok=false` - дамп не удался; `copied=false` - копия на C: не сделана.
Папка `~/nexus-backup-status` (`BACKUP_STATUS_DIR`) подключается к контейнеру `worker-maintenance` только для чтения как `/backups`;
сами дампы в контейнер не попадают (папка дампов закрыта правами 0700, а контейнер работает от другого пользователя).
`make up-local` создаёт эту папку сам.

## Тест на неделю (soak): чтобы Windows не уснул
Бэкап в 03:15 и сканер работают, только пока компьютер и WSL не спят. Один раз перед запуском:
1. Параметры Windows - Система - Питание (Power & battery) - Экран и спящий режим: "Перевод устройства в спящий режим" -> **Никогда**
   (для питания от сети; у ноутбука также от батареи).
2. Или в PowerShell (от администратора): `powercfg /change standby-timeout-ac 0` и `powercfg /change hibernate-timeout-ac 0`.
3. Не закрывайте крышку ноутбука (Панель управления - Электропитание - Действие при закрытии крышки - "Действие не требуется").
4. Не выполняйте `wsl --shutdown`; перезагрузку Windows откладывайте (обновления) - каждая остановка попадёт в простой в отчёте.
Проверка перед уходом: `powercfg /query SCHEME_CURRENT SUB_SLEEP STANDBYIDLE` (значение AC должно быть 0x00000000).

## Перезапуски сканера
Сканер перезапускается без ограничения числа попыток при любом сбое (Docker сам увеличивает паузу между попытками).
Исключение: отказ по политике ключей (код выхода 3) - контейнер останавливается и не крутится в цикле. Тогда в журнале
(`make logs`) будет строка "refused the key policy"; исправьте ключи и запустите сканер вручную. Обычная остановка (`stop`) тоже не вызывает перезапуск.

## Копия на другой компьютер
Необязательно и только с вашего согласия. Перед копированием файл шифруется:
`age -r <публичный-ключ> -o файл.dump.age файл.dump` (или `gpg --encrypt`). Незашифрованный дамп
за пределы этого компьютера не отправляйте.
