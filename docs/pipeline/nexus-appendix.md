# Nexus project appendix (from adoption instructions)

Это приложение **дополняет** общие правила выше и имеет приоритет там, где уточняет их.

### P1. Идентичность
Проект **Nexus** (Nexus Spread Scanner). Точное имя репозитория, ветки и версии возьми из git (`git remote -v`, теги), не предполагай. Существующая шапка README (логотип, название, бейджи, стиль) сохраняется.

### P2. Что известно заранее (со слов пользователя и README; ВСЁ проверить аудитом)
- Асинхронный сканер арбитражных спредов между централизованными биржами (CEX): спот-рынки Bybit, Binance, OKX, Gate.io, KuCoin. Оценивает **чистый** спред после комиссий тейкера на обеих ногах, проскальзывания по стакану и стоимости сетевого перевода, шлёт оповещения в Telegram, сохраняет все оценки в PostgreSQL для анализа.
- Стек по README: Python 3.12, `mypy --strict`, `ruff`, Docker Compose, PostgreSQL; вероятно Redis/Celery (проверить).
- Статус по README: «V1 read-only scanner». Проект сформирован и запущен локально в Docker, нужен глубокий аудит и улучшения.
- Пользователь упоминает работу и с CEX, и с DEX, а также газ и межсетевые взаимодействия. **Если в коде нет DEX-ноги, не добавляй её сам:** выясни, входит ли она в цели (вопрос в U0/U2) и как соотносится с текущим объёмом.
- Это идея, где конкуренция высока (многие боты следят за теми же спредами), поэтому вердикт «стабильного плюса нет» (NO-GO) — нормальный и честный исход, а не провал работы агентов.

### P3. Предзаполненные ответы на вводные вопросы (показать пользователю одним сообщением: «верно / поправь»)
- **A. Стадия:** MVP / анализ (сканер работает, гипотеза «можно ли стабильно зарабатывать на спреде» ещё проверяется). Аудит подтвердит или поправит.
- **B. Протокол развилки GO / NO-GO:** да.
- **Цель:** (1) понять по данным, возможен ли стабильный «плюс к депозиту» после всех издержек; (2) привести код и архитектуру в порядок; (3) при GO — развернуть промышленно (Стадия 2) и развивать (Стадия 3); при NO-GO — упаковать как проект для портфолио.
- **Порог «плюс к депозиту»:** спросить (варианты: 1% / 2% / 3% в месяц на выделенный капитал / свой; ориентир капитала $10–20k USDT, подтвердить). Реальный уровень покажет модель `quant-analyst`, а не пожелание.
- **Что трогать нельзя:** ничего без тестов; боевых ключей биржи у агентов нет и не будет на Стадии 1; реальные торговые операции запрещены до GO и явного подтверждения пользователя.
- **Глубина вмешательства:** аудит, исправления, рефакторинг, оптимизация математики и производительности; новые функции (DEX, новые биржи и др.) только после утверждения карты (U2).
- **Интерфейс:** **полноценного GUI/фронтенда не будет**, только аналитические дашборды и графики (на Стадии 2 они доступны на сервере под защитой). Агенты `frontend-lead` и `designer` не создаются.
- **Docker:** остаётся основой запуска (локально и на сервере) при любом исходе.
- **Автономность:** по умолчанию (вопросы только в точках участия).
- **Существующие правила для ИИ:** сохранить и перенести (проверить наличие).
- **Бюджет:** без платных сервисов без согласования; дашборды только на бесплатных/open-source решениях.

### P4. Состав команды
Обязательные роли (заказ пользователя) + базовые из общего шаблона. **Не ограничивайся этим списком:** в Фазе 3 проверь пробелы и добавь недостающих специалистов (по правилам «Расширение состава», до 3 без вопроса пользователю).

| Агент | Роль в Nexus |
|---|---|
| `orchestrator`, `analyzer`, `project-manager`, `scribe` | Базовые: управление, аудит, задачи, сводки. |
| `lawyer` (юрист / compliance) | Регуляторные и юридические риски: CEX/DEX, блокировки аккаунтов, условия использования (ToS), налоги, юрисдикции. |
| `quant-analyst` (математик / квант-алгоритмист) | Проверка математики и жизнеспособности: возможен ли стабильный заработок на спреде с учётом комиссий, газа, сетевых сборов и задержек. |
| `architect` + `tech-lead` (системный архитектор и тимлид) | Аудит и оптимизация архитектуры, взаимодействия сервисов и асинхронных процессов; ревью стадий. |
| `backend-lead` (бэкенд) | Оптимизация кода, работы с БД и очередями, исправление багов и утечек. |
| `crypto-specialist` | Специфика CEX/DEX, сетей, газа, переводов между площадками, ограничений API. |
| `observability-engineer` (аналитик / observability) | Сбор метрик и результатов, аналитика, графики и дашборды (Grafana / Superset / Metabase или аналоги). |
| `tester`, `security`, `devops` | Базовые: страховочные и интеграционные тесты, безопасность (ключи, секреты, Docker), CI/CD и сервер. |

Кандидаты в дополнительные роли (решай по аудиту): `data-engineer` (хранение временных рядов: партиционирование, ретеншн, объём таблиц), `performance-engineer` (задержки, asyncio, профилирование), `risk-manager` (для Стадии 2: лимиты, аварийный выключатель, управление экспозицией), `dex-engineer` (если в объём входит DEX-нога: пулы AMM, газ, MEV), `compliance-officer` (если юрист укажет лицензионные требования). Для роли вне списка опиши её с нуля по шаблону агента.
Выбор стека дашбордов (Grafana / Superset / Metabase) фиксируется в ADR: ориентир — Grafana для временных рядов и метрик сервиса (источники: PostgreSQL и Prometheus), Superset/Metabase для SQL-аналитики и срезов; допустимо сочетание, если оно оправдано ресурсами.

### P5. Задачи ключевых ролей
**`lawyer` (результат: `docs/legal/nexus-risk-assessment.md`, предварительная оценка, не юридическая консультация; со ссылками на источники; вопросы для живого юриста помечены).** Проверить:
- условия использования API и данных каждой из пяти бирж (автоматизированный доступ, лимиты, перераспространение данных, ограничения по странам и по типам аккаунтов);
- риски блокировки или заморозки аккаунтов при автоматической торговле и переводах между биржами; требования KYC;
- запрещённые практики (манипулирование рынком, wash trading, использование нескольких аккаунтов) и как они соотносятся с задуманной логикой;
- DEX: санкционные риски адресов, риски смарт-контрактов, правила использования агрегаторов;
- юрисдикция пользователя (Аргентина): регулирование криптоактивов и поставщиков услуг, налогообложение доходов от торговли, валютные ограничения; ответственность и учёт операций;
- хранение и обработка данных (Telegram, логи), лицензии зависимостей, раскрытие рисков в README при публикации как портфолио.
Вердикт юриста — часть критериев GO: блокирующий юридический риск = нельзя переходить к реальным деньгам.

**`quant-analyst` (результаты: `docs/quant/`: модель издержек, отчёт о проверке формул, анализ жизнеспособности, вердикт).** Проверить и сделать:
1. Независимо переписать формулу чистого спреда и сверить с кодом на наборе эталонных примеров; все деньги и цены в `Decimal`; единицы измерения, шаги цены и объёма, минимальные суммы ордеров.
2. Реалистичная модель издержек: комиссии тейкера/мейкера с учётом уровней и скидок, комиссии на вывод по каждой сети и актуальные минимумы, проскальзывание как проход по стакану на нужный объём (глубина, а не лучшая цена), газ для DEX-ноги.
3. Задержки и «время жизни» спреда: измерить, как быстро спред исчезает, и сравнить с реальной задержкой полного цикла (получение данных, решение, отправка ордеров на двух площадках); устаревшие котировки и «призрачная» ликвидность не считать возможностью.
4. Два режима исполнения и их экономика: (a) с переводом активов между биржами на каждую сделку (сетевые сборы, время подтверждения, риск изменения цены в пути); (b) с заранее распределёнными балансами на биржах (без переводов в каждой сделке, но с затратами на ребалансировку и замороженным капиталом). Оценить требуемый капитал и его эффективность.
5. Доходность на капитал: чистая прибыль в месяц на выделенный капитал, распределение результатов (медиана, квантили, худшие периоды), доля исполнимых возможностей, риск незавершённой второй ноги (частичное исполнение, отказ).
6. Честная проверка: разделение данных на подбор параметров и отложенные данные (последовательная проверка, без подглядывания в будущее), поправка на множественные проверки, учёт исключённых/делистингованных пар, чувствительность к допущениям (задержка, комиссии, объём), устойчивость по дням и режимам волатильности.
7. Вердикт `docs/quant/viability-verdict.md`: возможен ли стабильный «плюс к депозиту» на выбранном пороге, при каких условиях, с какой уверенностью, что опровергло бы вывод. Без приукрашивания.

**`architect` + `tech-lead`:** карта сервисов и потоков данных; корректность асинхронных процессов (отмена задач, таймауты, повторные подключения и повторные подписки, обратное давление, синхронизация часов, синхронность снимков и обновлений стакана); уместность Celery/Redis для задач сканера; идемпотентность; отказоустойчивость при сбое одной биржи; границы модулей и интерфейсы (`IDataSource`-подобные абстракции для бирж, чтобы новые источники добавлялись без правки ядра); конфигурация и изоляция контейнеров; план миграции к целевой архитектуре малыми шагами.

**`backend-lead`:** профилирование и исправление утечек (память, соединения, дескрипторы, задачи asyncio), индексы и структура таблиц оценок, пакетная запись, пулы соединений, политика хранения и сжатия данных, рост БД, очереди (длина, повторы, мёртвые письма), производительность горячих путей; всё с замерами до и после и тестами.

**`crypto-specialist`:** особенности REST/WebSocket API каждой из пяти бирж (лимиты, различия формата и глубины стакана, согласованность снимка и дельт, пересинхронизация, ограничения на подписки); сопоставление символов и активов (один и тот же тикер может быть разными активами, различия сетей ERC-20 / BEP-20 / TRC-20 и др.), статусы ввода/вывода и сбои вывода, мемо/теги, делистинги и приостановки; комиссии вывода по сетям; для DEX: AMM-математика, глубина пулов, газ, MEV, агрегаторы; для межсетевых переводов: мосты, финальность, риски.

**`observability-engineer`:** инструментирование метрик (количество оценок, найденных возможностей, чистый спред до и после издержек, задержки по этапам, лаг данных по биржам, ошибки API, длины очередей, использование памяти), структурные логи; дашборды как код в репозитории (провижининг источников данных и панелей, JSON/YAML в `infra/` или `observability/`); сервисы мониторинга в `docker-compose` (локально) и в production-compose; оповещения о проблемах (лаг данных, падение биржи, рост очередей) в Telegram. Набор панелей: распределение чистых спредов, число возможностей по дням/часам/парам/маршрутам, ожидаемая чистая прибыль (медиана, сумма), доля исполнимых, время жизни спреда против задержки, здоровье бирж, использование ресурсов; после GO: **ТОП прибыли по дням, месяцам, сделкам, парам и маршрутам**, фактическая против расчётной прибыль, накопительный график. Доступ к дашбордам на сервере только под защитой (аутентификация, HTTPS, ограничение по IP/VPN). Интерфейса, кроме дашбордов, не создавать.

### P6. Критерии GO / NO-GO (определить цифры с пользователем в начале M3 и зафиксировать в `todo.md`)
- **Обязательно:** «плюс к депозиту» на согласованном пороге в % в месяц, на отложенных данных, с учётом всех издержек и затрат на капитал/ребалансировку (см. P5, `quant-analyst`).
- Число возможностей в день/неделю выше порога после издержек и их стабильность не меньше срока в 7–14 дней и в разных режимах волатильности.
- Медиана и среднее ожидаемой чистой прибыли положительны; результат не держится на 1–2 парах или одной бирже (ограничение концентрации, значение согласовать).
- Время жизни спреда заметно больше измеренной задержки полного цикла (с запасом); доля исполнимых возможностей по глубине стакана достаточна.
- Требуемый капитал и ребалансировка укладываются в доступные средства пользователя.
- Юридический вердикт без блокирующих рисков.
- Качество данных подтверждено (нет перекосов из-за устаревших котировок, пропусков, ошибок сопоставления активов).
Если критерии не выполнены, исход NO-GO или «Доработать» (изменить гипотезу: другие пары/сети/режим с заранее распределёнными балансами, другие площадки).

### P7. Стадии 2 и 3 для Nexus (только после GO и подтверждения пользователя)
**Стадия 2: промышленное развёртывание + core-система.** Движок исполнения (две ноги, состояние ордеров, сверка, отмена и закрытие незавершённой ноги), модель с заранее распределёнными балансами или переводами по решению `quant-analyst`, менеджер риска (лимиты на сделку, на площадку, на день; защита от устаревших данных; аварийный выключатель), учёт фактической прибыли против расчётной, торговые ключи только с правом торговли и **без права вывода средств** и с привязкой к IP сервера, старт с минимальной суммы, уведомления в Telegram, CI/CD на VPS (Docker, миграции, healthchecks, автооткат), мониторинг и дашборды на сервере. Гайд для пользователя (сервер, ключи) создаётся файлом перед стадией.
**Стадия 3: развитие.** Расширение охвата (новые биржи, DEX-нога, другие типы спредов, треугольные цепочки, перп-спреды), оптимизация стратегий по реальным данным, расширенные дашборды (ТОПы прибыли по дням/месяцам/сделкам), алерты, бэкапы, масштабирование воркеров. GUI не создаётся.

### P8. Идентичность при NO-GO (упаковка в портфолио)
Проект подаётся как **«Cross-Exchange Spread Analytics Toolkit»**: инструмент для измерения реально исполнимых межбиржевых спредов после всех издержек, со стаканной моделью проскальзывания, моделью издержек, хранилищем наблюдений, дашбордами (Grafana или выбранный стек) и воспроизводимым исследованием результатов. Docker и CI/CD остаются (деплой только ручной, без реального развёртывания), контейнеры и тома, запущенные локально, удаляются после сохранения результатов в репозитории. Слово «pet» нигде не используется.

### P9. Особые ограничения
- Агенты не получают боевых ключей бирж и не совершают реальных операций; на Стадии 1 только публичные данные (read-only).
- Не разрушать накопленные данные в БД: перед миграциями и чисткой томов делать резервную копию и подтверждение (U4).
- Секреты (токен Telegram, ключи бирж) не печатать и не коммитить; если они найдены в репозитории или истории, описать место и тип, рекомендовать пользователю заменить.
- Внутри Docker любые тяжёлые анализы выполнять на копии данных.

### P10. Первые шаги (порядок)
1. Фаза 0: страховка (ветка, тег), разведка, подтверждение предзаполненных ответов (P3), недостающие вопросы.
2. Фаза 1–2: аудит всех областей; отдельный упор на: проверенные команды запуска в Docker, корректность формул, асинхронность и утечки, объём и рост БД, секреты, юридические вопросы; определение стадии.
3. Фаза 3: уточнение состава команды (P4) и пробелов (U1).
4. Фаза 4: Claude-файлы, документация, дашборды как задача `observability-engineer`.
5. Фаза 5: видение и целевая архитектура, карта (U2).
6. Траектория M: M1 → M2 (математика, баги, утечки, производительность) → M3 (данные, `quant-analyst`, юрист, отчёт) → M4 (точка UF: GO / Доработать / NO-GO).
